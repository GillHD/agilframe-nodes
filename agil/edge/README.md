# AGIL Edge

## Публикация MP4 в SFU-комнату

Операторский процесс читает готовый MP4, передаёт дорожки через FFmpeg
без перекодирования и публикует их в SFU-комнату через LiveKit Ingress.
Подготовьте один видеотрек H.264 `yuv420p` и один аудиотрек AAC-LC
с одним или двумя каналами на 44,1 или 48 кГц. Файл зацикливается, чтобы
проверить воспроизведение и остановку публикации на одном источнике.

Нужны Node.js 20 или новее, FFmpeg и FFprobe. На Core включите Redis
для Flows и настройте управляемый RTMP Ingress. Заранее создайте
SFU-комнату в организации, которой принадлежит ключ управления.
[Настройка Core и LiveKit Ingress](../core/docs/flows.md#managed-rtmp-push)

Запускайте контроллер от выделенной учётной записи на доверенном узле
оператора. Он использует существующий административный ключ организации.
Для входа укажите абсолютный путь к локальному файлу. `--ingress` задаёт
ожидаемый адрес публикации без пути и ключа. Адрес ведёт на разрешённый
RTMPS-вход. Для локальной проверки разрешены HTTP и RTMP на числовом
loopback-адресе. При RTMPS Node проверяет сертификат и имя Ingress перед
передачей данных. FFmpeg соединяется с временным локальным портом.

```bash
read -rs -p 'Tenant API key: ' AGIL_EDGE_CORE_API_KEY
export AGIL_EDGE_CORE_API_KEY
node agil/edge/agent/run-rtmp-publisher.mjs \
  --core https://core.example.org \
  --ingress rtmps://publish.example.org:443 \
  --room studio \
  --input /srv/edge/media/studio.mp4
unset AGIL_EDGE_CORE_API_KEY
```

Контроллер создаёт новый Flow с уникальным идентификатором и получает
ключ публикации. Каждая сессия владеет своим Flow. В журналах указываются
идентификатор и стадия `creating`, `connecting`, `ready`, `degraded`,
`stopped` или `failed`. Стадия `ready` означает, что Ingress подтвердил
состояние `publishing`. Выход из `ready` означает, что приём медиа
временно потерян. После 45 секунд ожидания процесс очищает свой Flow.

При `SIGINT` или `SIGTERM` контроллер останавливает FFmpeg и удаляет свой
Flow. Core при удалении отзывает Ingress. Если Core недоступен или ответ
на мутацию потерян, журнал сохраняет идентификатор. После восстановления
проверьте этот Flow в панели или HTTP API и удалите его при необходимости.
При временной ошибке отзыва контроллер повторяет запрос для своего Flow.
Ключ управления остаётся в контроллере. Ключ публикации нужен FFmpeg и
может быть виден локальным процессам с доступом к аргументам FFmpeg.

### Локальная проверка

```bash
AGIL_QA_MEDIAMTX_BIN=/absolute/path/to/mediamtx \
  node --test agil/edge/test/rtmp-publisher.test.mjs
```

Этот тест запускает FFmpeg и MediaMTX на loopback. Тестовый HTTP-контроллер
отвечает по контракту Flow и получает фактическую готовность из MediaMTX.
FFprobe читает опубликованные H.264 и AAC. После остановки вход больше
не готов, а тест подтверждает запрос удаления конкретного Flow.

Тесты RTMPS создают временные сертификаты и проверяют публикацию с
подходящим именем, а также отказ при доверенном сертификате для другого
имени.

Для сквозной проверки на изолированном Linux-стенде с Chromium и
локальным Docker соберите Core-зависимости и виджет. Загрузите образы
`redis:7-alpine`, `livekit/livekit-server:v1.13.11` и
`livekit/ingress:v1.6.0`. Сквозной сценарий использует порты 39541–39547.

```bash
node --import tsx agil/edge/test/rtmp-livekit-e2e.mjs
```

Сценарий проверяет декодированные кадры и звук в Chromium, отсутствие
созданного Flow и отозванный приёмник после остановки.
